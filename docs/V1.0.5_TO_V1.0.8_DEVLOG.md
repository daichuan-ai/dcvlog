# V1.0.5 → V1.1.0 实机测试与产品决策记录

这份记录用于后续开发，防止已经验证过的问题再次被“修回去”。

## V1.0.5：核心内容逻辑基线

后续版本必须优先保护以下能力：

- 采访式创作：先聊事实，不先写稿；
- AI 先进入目标客户的脑子，再采访化妆师；
- 一次只问一个现实问题；
- 前台像老师坐旁边聊天，后台结构隐藏；
- 用户卡壳时，不继续逼问，先鼓励和给成熟表达参考；
- AI 提示出来的专业表达必须再确认：是否本人真实判断、是否有画面支撑；
- “事实不等于素材”，低价值真话可以不写；
- 多客人先分别采访，再统一装配整条 Vlog；
- 前5秒单独选择真实素材：强画面/真实数字/本人审美人设/文案钩子兜底；
- 正文结束后可做轻人设收口，但不强行升华；
- 完整稿最后再做本人语气定型，只微调口语节奏；
- AI整理优先保护真人语料，不把每句话改成标准 AI 文案腔；
- 提问深度应等于目标观众愿意听懂的深度，不等于老师能讲多深。

## 两轮早期实机采访发现

第一轮证明主采访链能跑，但成稿容易过于结构化、结尾被 AI 强行升华、会出现内部流程泄露。

第二轮出现“脸宽显胖 → 脸侧修容 → 发型做大 → 头包脸”的真实卡壳过程。确认“不知道/说不出来/都不是/你来定”不是普通答案，而是疲劳/卡住信号；这时必须停掉正常追问，改用陪跑救援。

由此形成：聊天式陪跑、成熟语料唤醒、意思确认、画面确认、低价值事实丢弃。

## V1.0.6：独特暗号实验

曾尝试用“代川妆造Vlog编导开工”和固定“川导开工”回执增强路由。

实测结论：如果 Skill 没有被宿主真正发现/加载，暗号再特别也无效。并且固定“川导开工”对普通学员来说生硬难懂，只适合开发阶段验明身份，正式产品应删除。

## WorkBuddy：云端、本地与手机远程不是同一层

实测出现：某个云端任务显示文件已下载并校验，但新的云端任务无法稳定发现；手机远程电脑又可能使用电脑本地 Skill。

因此必须区分：本地电脑 Skill、当前云端沙箱 Skill、宿主持久注册 Skill。

“文件下载成功”不等于“以后所有新任务都能用”。

## V1.0.7：引入 `/dcvlog`

斜杠显式调用比自然语言自动路由稳定。`/dcvlog` 被保留为长期主入口。

但当时仓库仍叫 `dc-makeup-vlog`，内部 Skill 已改成 `dcvlog`，身份不统一。

## 豆包工作：替代 Skill 污染测试环境

一次安装失败后，宿主没有安装 GitHub 真 Skill，而是根据历史上下文自动生成了一个相似 Skill；这个假 Skill 随后出现在技能列表中，内容包含旧六段式、40—50秒、朋友圈框架等，与 DCVlog 无关。

重要结论：

- “聊天里说安装完成”不能作为验收；
- 安装失败时必须禁止宿主创建替代 Skill；
- 必须核对唯一 GitHub 身份；
- 测试前要清理宿主自己生成的假 Skill；
- 安装之前宿主看不到真正 SKILL.md，因此仓库定位问题不能只靠 Skill 正文解决。

## V1.0.8 豆包工作真实调用成功

新对话输入 `/dcvlog` 后，宿主成功定位到类似 `/home/user/.agents/skills/dcvlog` 的真实安装目录，读取 Skill 说明并进入采访。

这证明：即使技能选择按钮里暂时看不到，斜杠入口仍可以稳定调用已安装 Skill。

因此验收标准调整：**技能菜单可见是加分项，不再是运行成功的必要条件；`/dcvlog` 能定位真实 Skill 才是当前最关键的实机标准。**

## V1.0.8 调用后发现的两个回归问题

1. 固定“好，川导开工”太像开发口令，普通学员难懂，正式版删除。
2. 新对话直接跳到了“今天这个客人来干嘛”，没有先认识化妆师。原因是此前为了简化调用，把启动逻辑写成“如果上下文似乎知道用户是谁就跳过”。宿主可能利用历史上下文/记忆误判。

V1.1.0 修正为：只看**当前对话线程**是否已经主动提供人物资料。新对话首次使用必须先认识化妆师，除非用户明确要求跳过或继续上次。

## V1.1.0：当前整合基线

完整运行顺序：

`/dcvlog → 当前对话首次人物认识 → 今天客人数 → 逐个客人聊天式采访 → AI后台选唯一主线 → 卡壳救援/证据确认 → 前5秒选择 → 多客人装配 → 可选人设结尾 → 完整连续旁白 → 本人语气定型 → 最终可直接录音版`

后续任何版本如果修改安装、路由或 UI，不得再次删掉上述内容层。
