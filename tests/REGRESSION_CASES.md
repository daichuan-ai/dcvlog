# V1.5.2 回归用例

## Case 1｜新对话
`/dcvlog` → 先问年份/年龄段，再城市、从业时间、工作状态/业务。

## Case 2｜实际3个，视频只讲1个
用户：`今天实际画3个，但这条视频只讲1个。`
正确：记录实际3、视频1；另外两位退出本条流程；直接进入这位客人的明确切口。
错误：继续问“第1个客人大概什么情况/给我一个标签”。

## Case 3｜生日场景不能被带回五官问题
用户：`她今天晚上过生日，还带了黑裙子。`
正确：继续问她想要什么感觉、这个场景影响了什么服务决定。
错误：立刻问`你第一眼觉得她脸哪里需要改？`

## Case 4｜领证可以直接成为主线
用户：`下午三点去领证，想自然一点。`
允许成稿主要围绕领证场景与自然需求，不强制补完整面诊。

## Case 5｜客户普通话不专业也有效
用户：`她就说不要太浓，拍照好看一点。`
不得自动改成“提升面部折叠度/量感”。

## Case 6｜问题型才深挖必要专业判断
用户主线：`每次化妆都显成熟。`
可以追一个真正原因和1—2个关键动作，但仍不做整脸清单。

## Case 7｜变化型
用户：`平时都是甜妹，今天想换个完全不一样的。`
写方向变化，不重新罗列所有五官。

## Case 8｜专业判断不是必答项
场景与需求已经讲通时，最终稿可以没有详细五官分析。

## Case 9｜辅料不能抢主线
主线是生日场景，采访中又出现“眼睛有点肿”。眼睛只在影响服务决定时出现，不能自动升级为整条主题。

## Case 10｜标准镜头
不得询问妆前、过程、妆后、拍照修图等标准镜头是否存在。

## Case 11｜前5秒四方向
最后才问；固定强画面/强情绪/强数字/纯文案；不能新增第五类。
强画面=化妆师主角型工作室/本人开场，不是随便一个漂亮镜头。

## Case 12｜强情绪与强数字
强情绪没有真实现场原声就不用；使用时必须标“（视频原声）/（现场原声）”。
强数字没有可展示截图/页面/录屏，不使用数字型开场。

## Case 13｜成熟锚点必须参与
最终稿前必须选择1个最接近的成熟锚点，不能只靠AI默认写作。

## Case 14｜锚点不移植事实
成熟样本是“领证白裙”，当前客人是“生日黑裙”，只能借结构，不能写进白裙/头纱。

## Case 15｜同类型长度比较
场景型最终稿必须优先与场景型成熟样本比较，而不是和问题型长稿比较。

## Case 16｜长度过长
同类成熟样本中位数120有效字，初稿190字 → 必须删到接近108—132字，不得仅改成两个超长复句。

## Case 17｜长度偏短
同类样本120字，但本次真实素材只能完整写80字 → 不允许编客户反馈/专业判断凑到120。

## Case 18｜删除顺序
超长时先删无关背景、第二第三个面部观察、无关步骤、重复解释、结果后升华。

## Case 19｜句子密度
不能为了字数接近，把“背景+需求+五官+动作+结果”塞进一句。

## Case 20｜结果回应主线
前面讲“不想太浓”，结果应回应自然/接受度；不能突然把“脸小了”作为结论。

## Case 21｜结果后停止
客户真实反馈已经完成证明后，不得追加“好的妆容就是……”升华。

## Case 22｜多客人递减
客人1最重，客人2缩短，客人3/4继续缩；总长度与同客人数成熟样本比较。

## Case 23｜命中人设方向后直接给结尾
用户：`我比较负责任，能给每个人定制化化妆。`
正确：最多给2个3—4秒成品，如“我是化妆超负责任的化妆师XX，今天就到这里，拜拜。”
错误：继续解释“每个人情况不一样，所以我不会画一样的妆”。
用户犹豫就放过，不硬造差异化。

## Case 24｜语气
结构与长度完成后再试读选语气；只做微调，不拉长稿件。

## Case 25｜运行文件瘦身
SKILL运行时只能引用7个核心 reference；开发日志和 tests 不得列为运行必读。


## Case 26｜单客切口不能宽泛
用户已确认本条只讲1个客人，但未说主线。
正确：直接给场景/需求/问题/变化/帮我找五个切口。
错误：问“这个客人大概什么情况”“她有什么特别”。

## Case 27｜主角型强画面
用户有漂亮工作室远中近景 + 自己高审美自拍。
正确：调用年龄/城市/工作状态/真实特点，写身份型Vlog开场；随后客人进门。
错误：只写“今天工作室好漂亮”。

## Case 28｜没有主角强画面就客人直入
用户没有工作室/本人强画面。
正确：可从客人坐下和脸部画面直接进入客人场景/需求/问题。

## Case 29｜开场结尾强词但事实不夸大
允许“超负责任/超级细节控/最会替客人操心”等与用户真实方向一致的人设表达。
禁止无依据“绵阳第一/行业唯一/全城最厉害”。


## Case 30｜两个客人不能同权重
用户要求一条视频写2位客人。
正确：第1位完整讲主故事；第2位只保留与第1位相比最值得看的一个新点 + 一个关键处理/服务决定 + 结果。
错误：第2位再次完整走“背景—需求—分析—步骤—结果”，只是字数略短。

## Case 31｜三个客人必须继续递减
正确：第1位讲故事；第2位讲重点；第3位只带一个需求/特点/场景与结果，必要时主要靠画面。
错误：三位都获得相近字数和相近信息层级。

## Case 32｜多客人不能被40秒总上限卡死
用户：`今天这条写3个客人。`
正确：总时长随客人数自然增长，并继续执行叙事权重递减。
错误：因为单客常见约30—40秒，就强行把3位客人一起压进40秒。

## Case 33｜单客长度尺不能约束多客整条视频
正确：单客20多秒—30/40秒只用于单客；多客优先找同客人数/相近客人数成熟样本。若无样本，则按开场 + 第1位完整块 + 第2位重点块 + 第3位以后轻量块 + 结尾自然装配。
错误：拿单客110—170字/约40秒作为多客整条视频的总上限。

## V1.7.0 自维护与持续案例库回归

### R17-01｜“更新 DCVlog”不得误进文案采访
输入：`更新 DCVlog`
期望：直接进入更新逻辑；可执行环境运行 `npx -y skills add daichuan-ai/dcvlog -g --all`，不得先尝试 `skills update dcvlog`，不可执行环境只返回命令。


### R17-06｜local 来源也能更新
输入：当前宿主把 `dcvlog` 显示为 `local`，用户说“更新 DCVlog”。
期望：不要报“本地来源无法更新”后停住；不要要求用户重新描述更新内容；直接从 `daichuan-ai/dcvlog` 执行覆盖安装。命令成功后提示新开聊天/重新加载。

### R17-07｜更新失败不得现场造 Skill
输入：官方 GitHub 覆盖安装命令真实失败。
期望：报告关键错误和官方命令；不得自行生成、重建或改写一个本地 `dcvlog` 作为替代。

### R17-02｜新增案例不得立即污染当前方法
输入：`加入 DCVlog 新案例库` + 1篇新文案。
期望：原文与分析分开收录到 Batch 002；不得因为单篇案例直接改 `current-patterns.md`。

### R17-03｜扫描新案例库才允许升级方法
输入：`扫描新案例库，升级当前方法`
期望：比较 Batch 001、Batch 002 和当前规律；区分多案例稳定共性与个人口癖；确认后才更新 current-patterns 与 Corpus Version。

### R17-04｜第一批基准不可被覆盖
输入：新增案例与旧案例风格冲突。
期望：Batch 001 原文保持不变；新趋势只能进入新批次和当前规律，不改写旧原文。

### R17-05｜写稿必须读取当前案例规律
输入：普通单客 Vlog 写稿。
期望：成稿前读取 corpus-index 与 current-patterns，再做同类型成熟样本结构/长度校准；不得只靠旧静态词库。

## V1.8.1 CloudBase 匿名统计回归

### T1｜统计不可达不得影响功能
- CloudBase 接口超时、断网、宿主无 Python 或不允许执行本地脚本；
- 文案/拼图必须照常运行，不向普通学员暴露统计异常。

### T2｜不得上传内容
- 事件 payload 只能包含 `event_name`、随机 `anonymous_id`、`skill_version`；
- 不得出现用户输入、客户原话、照片、工作室名、城市、成稿正文、拼图文件内容。

### T3｜拼图完成严格按交付完整度
- 用户上传4张并选择“两种都要”；
- 只生成4张独立页时不得记录 `collage_complete`；
- 1张总拼图 + 4张独立页全部交付后才记录。

### T4｜事件白名单
- 只允许 `dcvlog_open / write_vlog_start / write_vlog_complete / collage_start / collage_complete / update_requested`；
- 其他事件名不得上报。

### T5｜匿名 ID 可复用但不可实名
- 同一可持久化环境复用 `~/.dcvlog/anonymous_id`；
- 不读取姓名、手机号、微信、城市、工作室名作为 ID。

### T6｜用户可退出
- `DCVLOG_TELEMETRY=0` 或 `~/.dcvlog/no_telemetry` 存在时不发送事件；
- 退出统计不得改变 Skill 其他功能。

## V1.8.4 审美采访与反模板成稿回归

### W184-01｜粉色生日裙不能直接落稿
输入：广州11年化妆师；客人过生日、穿粉色裙子；粉色眼影腮红唇色；“很满意”。
期望：确认主线后还追问一个真实人物/服装印象或审美取舍、一个妆后可见状态；不能生成固定“她照镜子可开心了”。

### W184-02｜同模具复写失败
输入A：卡其毛领一字肩→贵气千金；输入B：粉裙→韩式甜妹。
期望：生成的两条必须基于各自确认事实有不同的人物或风格选择，不能仅换颜色和称呼；信息不足应补问而不是补形容词。

### W184-03｜小白只会说细节
用户答：“黑眼圈、中庭、眼线拉长、睫毛加重。”
期望：问一个普通人能回答的整个人原本/妆后印象，帮她从专业操作回到人物感受；不直接罗列成教程。

### W184-04｜卡壳两次
用户连续答：“不知道”“都不是”。
期望：最多给可选的真实感受方向；两次仍无法确认则提出自愿发妆后图，或以克制版留白并明示缺口；不得代客人捏造结局。

### W184-05｜客户反馈不是画面
输入：“她照镜子笑了，说满意。”但没有妆后变化描述。
期望：继续追问画面或让真实成片承接；不能仅以笑、满意、很适合作为“结果画面”完成闸门。

### W184-06｜场景型不必强问五官
输入：“穿黑裙领证，想自然，化妆师确实决定眼妆做轻，妆后看起来很干净、精神。”
期望：无需编造鼻基底、泪沟、中庭，可顺着服装和场景成文；结果对应已确认状态。

### W184-07｜完妆比喻必须有锚点
输入：“她下垂眼给人软萌感，完妆显得眼睛圆亮。”
期望：可做自然的兔子意象联想，但不能擅加客人自拍、朋友夸、实际尖叫等情节。

### W184-08｜新娘甜转清冷的单一重点
输入：“本身甜、想清冷、五套造型、口红变化。”
期望：以甜→清冷为唯一核心，五套服装信息只有服务主线才进稿，不写成彩妆清单。

### W184-09｜教师面试不是化妆教学
输入：“考教师岗，客户原话不要浓，要亲和。”
期望：一条真实约妆工作故事，不是“转色遮瑕→粉底→眉眼→口红”的教学口播；真实结果未提供必须补问。

### W184-10｜原始案例逐字可用且单客校准
`Batch003/cases.md` 含19个编号，原文不改；单客稿只能参照03—10、12—19内部的对应客人段，不能拿三客全文总字数作单客标尺。

### W184-11｜非写作模块不退化
拼图比例与裁切规则保持V1.8.3行为；遥测仍只发送匿名功能事件，不能收集用户原文、成稿或照片。
