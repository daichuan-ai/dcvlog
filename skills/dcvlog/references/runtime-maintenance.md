# 运行维护｜按当前操作读取

启动更新由主入口执行；匿名事件、仅约妆的自愿收稿、维护更新和案例管理见下文。此文件不参与新娘文案创作。

### 匿名使用统计｜后台静默、绝不打断任务

继续使用腾讯云 CloudBase 匿名功能事件统计。配置见 `telemetry-config.json` 与仓库 `docs/ANALYTICS_SETUP.md`。

**统计只允许记录功能事件，不允许记录任何内容。**V1.8.7新加的独立、自愿收稿在下节，不得与事件统计混合。

允许事件：`dcvlog_open`（进入）、`write_vlog_start / write_vlog_complete`（写稿开始/完成）、`update_requested`（明确更新）。

如果宿主允许执行本地脚本，在对应节点 best-effort 调用当前 Skill 自带的 `tools/telemetry.py <event>`。

硬规则：

1. 统计调用必须静默，不对普通学员显示“正在上报/统计成功”等话术；
2. 统计失败、断网、脚本不可执行或统计接口不可达时，**直接跳过**，不得影响正常任务；
3. 禁止把用户输入、客户故事、照片、生成文案、工作室名、签名名、城市、文件名等作为事件属性；
4. 只使用本地随机匿名 ID 粗略区分安装环境，不建立实名人物资料；
5. 普通问答轮次不统计，避免把“聊得多”误当成“用得多”。

触发建议：

- `/DCVlog`（大小写等价的 `/dcvlog`）：`dcvlog_open`；
- 选择1进入约妆文案模式：`write_vlog_start`；交付最终稿：`write_vlog_complete`；选2和选3不触发这两个写稿事件；
- 命中自然语言更新：`update_requested`。

### 可选完稿回收｜独立接口、首次同意、可拒绝

**仅首屏选1的约妆文案模式**在进入正式采访时读取 `@references/review-collection.md`；跟妆和真实表达流程不触发。选3不得调用 `review_upload.py` 的 `status / agree / submit`，不得沿用约妆的共享许可上传或虚填客人数；本人明确退出既有收稿时仍保留调用 `decline` 的权利。操作顺序始终是：`/DCVlog` 静默查新 → 首屏选1 → 收稿许可状态检查（仅需要时问一次）→ 原有采访。该功能不能影响主线、妆后作品解读或文案输出，也不能取消原版匿名统计。

- 公开公测配置已启用独立地址；但**没有学员明确同意、宿主不支持执行工具或后台尚未开启公测时均不能上传**，不得声称已收集成功。
- 配置启用后，调用 `tools/review_upload.py status`：仅 `unset` 需要显示一次简短「同意/不同意」选择，`agreed/declined` 都不重复问；任何脚本、文件或状态读取失败均视为**不能上传**。
- 学员同意后，只对本次**已经完成的最终旁白**进行一次 best-effort 上传，绝不上传全文聊天、逐轮采访或照片。重要客户个人信息先剔除，程序再遮盖可识别的联系方式。仅返回含 `READY/LIMITED_DRAFT` 状态的成稿和可选、简短、确认过的依据摘要。
- 上传与否不影响交稿，失败不可谎称成功；若无法把正文安全交给上传脚本，就跳过，并在开发验收中记录该宿主能力缺口。学员任何时候表示退出收稿，调用 `decline`，未来停止上传。

### 自维护入口｜自然语言更新 DCVlog

如果用户明确说“更新 DCVlog”“升级 DCVlog”或“把 DCVlog 更新到最新版”：

**不要进入文案采访流程。不要先尝试 `skills update`，也不要先检查本地 Skill 有没有远程来源。**

原因：豆包工作等宿主里，DCVlog 可能被识别成 `local` 本地 Skill，`skills update dcvlog` 会出现 `No installed skills found matching: dcvlog`；官方安装器写入的全局路径也不一定是当前宿主加载路径。

如果当前宿主允许执行命令，先静默 best-effort 记录 `update_requested`，然后使用上节同一个 `tools/update_skill.py --skill-dir <实际加载目录>`。自动解析该目录的真实路径、核对官方提交、完整更新、保留备份并读回，不能只更新 `~/.agents/skills` 就宣布豆包已生效。不要自行生成替代 Skill，不修改官方来源，不把用户带进“你要改什么内容”的对话。

只有返回 `updated/up_to_date` 且 `verified:true` 才可确认文件已与官方当前提交一致；更新后按上节重读新入口。无法执行、联网或写入时说明限制；旧安装缺更新器时，给出从 `daichuan-ai/dcvlog` 完整安装一次新版、核对实际加载目录的指引。不能假装成功，也不能用现场改写 Skill 代替官方更新。

第一次还没安装时，Skill 自身无法负责“安装自己”。对外安装说明统一使用仓库 `daichuan-ai/dcvlog`。

### 案例库维护模式｜给代川持续喂新案例

本 Skill 的逻辑版本和成熟案例库版本分开维护。案例库索引见 `@references/corpus/corpus-index.md`。

当用户明确说：

> 加入 DCVlog 新案例库

进入【案例收录模式】，不要开始普通 Vlog 采访。用户贴来新案例后：

1. 原样保存到 `references/corpus/batch-002-new/`，编号从 `B002-001` 开始；原文与AI分析分开。
2. 记录类型、有效字数/句数/时长、开场、主线与结果位置；只总结值得学习的行为逻辑，单篇不升级为永久规则。
3. 有权限则写入Batch002；无写权限要明确说未写入，并提供可追加原文案例块，不得假装保存。

当用户明确说：

> 扫描新案例库，升级当前方法

进入【案例扫描模式】：

1. 读取 Batch 001 锁定基准、Batch 002 全部新增案例和 `current-patterns.md`；
2. 比较新的开场、主线、信息顺序、句子密度、结果位置、总长度和停止位置；
3. 区分“平台新趋势 / 多案例稳定共性 / 单个博主个人口癖”；
4. 只有多案例或有充分理由支持的新规律，才更新 `current-patterns.md`；
5. Batch 001 原文永不覆盖；
6. 更新方法后同时升级 `CORPUS_VERSION`，但不因为案例库变化强制改 Skill 逻辑版本；
7. 新旧案例冲突时，优先保留真实、证据和不编专业判断的硬规则。

普通学员写稿时，不显示这些维护细节。
